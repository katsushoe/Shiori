# Shiori v2.0.0 仕様案

**状態:** Draft  
**作成日:** 2026-08-22  
**位置付け:** Shiori v1.xからの破壊的変更を含む次期メジャーバージョン

## 1. 製品方針

Shiori v2.0.0は、AIエージェント向けのローカルファイル検索に責務を限定する。
コードの本文、構文、シンボル、参照関係を検索または解析する機能は提供しない。

優先順位は次のとおりとする。

1. ファイル本文を読み取らない高速なインデックス作成
2. ファイル名および相対パスの高速かつ予測可能な検索
3. 小さな配布物、少ない依存関係、単純な運用
4. 許可ワークスペース境界を越えないローカル完結動作

## 2. 対象ユースケース

Shioriは、利用者またはAIエージェントが「目的のファイルがどこにあるか」を発見するために使用する。
発見後のファイル読み取り、本文検索、コード解析、定義・参照移動は、AIエージェント、IDE、ripgrep、
言語サーバーなど利用側のツールが担当する。

## 3. 提供機能

### 3.1 インデックス

単一の中央SQLiteデータベースへ、除外後のファイルについて次の情報を
ワークスペースID付きで保存する。

- 正規化済み絶対パス
- ワークスペース相対パス
- ファイル名
- 拡張子
- ファイルサイズ
- 最終更新日時
- インデックス更新日時

ファイル本文、本文ハッシュ、言語判定結果、構文木、シンボル、シグネチャは保存しない。
インデックス作成処理は、ファイル本文を開かず、ディレクトリエントリとファイルメタデータだけを読む。

### 3.2 ファイル検索

検索対象はファイル名および相対パスとする。検索結果には少なくとも相対パス、絶対パス、
ファイルサイズ、最終更新日時を含める。検索はワークスペース単位で行い、既存の件数上限と
中央`shiori.db`の`Workspaces`テーブルによる認可境界を維持する。

検索順位は決定的でなければならない。同じインデックス、検索語、設定に対して同じ順序を返す。
Git情報による順位補正を維持する場合も、検索処理に明確な上限時間を設け、利用不能時は
パス一致だけの順位へフォールバックする。

### 3.3 インデックス状態

ワークスペース、状態、登録ファイル数、登録ディレクトリ数、最終走査日時、最終完了日時、
スキーマバージョンを返す。登録ディレクトリ数は正常公開時に進捗ログ表から確定保存し、
状態取得時に実ディレクトリを再走査しない。
シンボル数、パーサーバージョンなどコード解析固有の項目は削除する。

## 4. 廃止機能

次の機能および公開インターフェースを削除する。

- 本文検索（`search_text`）
- シンボル検索（`search_symbols`）
- AST検索（`search_ast`）
- ファイルアウトライン（`get_file_outline` / `outline`）
- LSPナビゲーション（`navigate`および定義、参照、実装、呼び出し階層の検索）
- 検索意図をコード検索へ振り分ける統合検索プランナー
- Tree-sitter、言語パーサー、ripgrep、LSPクライアントおよび言語サーバー検出
- シンボル、FTS、本文ハッシュ、言語情報を保持するデータベース構造

コード検索を無効化する互換モードは設けない。v1.xのコード検索APIを呼び出した場合は、
不明なMCPツールまたは不明なCLIコマンドとして扱う。

## 5. インデックス作成ツール

### 5.1 実行形態

`shiori index build <workspace>`および`shiori index rebuild <workspace>`は、
利用者が進行状況を確認できるコンソール上で実行する。

- コンソールから起動した場合は現在のコンソールへ表示する。
- コンソールを持たない対話セッションから起動するWindows版ランチャーは、専用の可視コンソール
  ウィンドウを作成してインデックス作成ツールを実行する。
- リダイレクト時はANSI制御文字や行上書きを使用せず、進捗を改行区切りで標準出力へ記録する。
- エラーの詳細は標準エラー、進捗と完了結果は標準出力へ出力する。
- 正常終了は終了コード`0`、入力・走査・保存の失敗は終了コード`1`とする。
- 処理終了後にキー入力待ちは行わない。親ランチャーが専用ウィンドウを作成した場合に限り、
  完了結果を確認できる短い終了猶予を設けてもよい。

MCPサーバーは検索要求の処理中にコンソールウィンドウを生成しない。インデックス更新は
明示的なインデックス作成ツールへ分離し、v1.xの`reindex`および`update_indexes` MCPツールは廃止する。

### 5.2 事前ディレクトリ計数

インデックス作成前に対象ワークスペースを走査し、処理対象となるディレクトリ総数を確定する。

- ワークスペースルート自身を1ディレクトリとして数える。
- `.gitignore`、Gitの除外設定、既定除外ディレクトリ、`SHIORI_EXCLUDE_PATTERNS`を適用した後に数える。
- シンボリックリンク、ジャンクションなどの再解析ポイントは追跡せず、リンク先を数えない。
- 同一ディレクトリを重複して数えない。
- 計数中は`対象ディレクトリを確認中...`と表示し、総数確定後に
  `対象ディレクトリ: N`と表示する。
- ルートへアクセスできない場合は処理を開始せず終了コード`1`で終了する。
- 子ディレクトリへアクセスできない場合は、既定ではエラーとして処理全体を中止する。
  不完全なインデックスを成功として保存してはならない。

事前計数とインデックス作成で同じ除外判定を共有し、両者の対象集合がずれないようにする。

### 5.3 ディレクトリ単位の進捗

インデックス作成は、事前計数で確定したディレクトリを1回ずつ処理する。各ディレクトリについて、
直下のファイルメタデータを列挙して保存対象へ追加し、そのディレクトリの列挙が正常に完了した時点で
完了ディレクトリ数を1増やす。

対話コンソールでは同じ行を更新し、少なくとも次の形式を表示する。

```text
30% 37/120 F:\Projects\ProjectA\src\components\example.cs
```

進捗値は次の規則に従う。

- 分子は正常に処理を完了したディレクトリ数、分母は事前計数した総ディレクトリ数とする。
- パーセントは`floor(完了数 * 100 / 総数)`で算出する。
- 開始時は`0/N (0%)`、全ディレクトリ処理後は`N/N (100%)`を必ず表示する。
- 表示パスは現在処理中のファイルの絶対パスとする。ディレクトリ完了時など対象ファイルが
  ない通知では、直前の処理対象ファイルまたはワークスペースの絶対パスを表示する。
- パスが表示幅を超える場合は末尾側を残して省略し、進捗数値を欠落させない。
- 端末出力の更新頻度は処理性能を損なわないよう抑制してよいが、完了数と100%は省略しない。
- 出力リダイレクト時は各ディレクトリ完了時に1行出力する。

100%表示は走査完了を表す。SQLiteトランザクションのコミット成功後、別途完了結果を表示する。

```text
インデクス作成が終了しました：F:\Projects\ProjectA（8421ファイル）
```

コミットに失敗した場合は100%表示後でも処理を失敗とし、完了メッセージを表示しない。
正常公開時は完了ディレクトリ数をSQLiteの索引状態へ保存する。CLIの`index status`と
MCPの`index_status`は、実ディレクトリを再走査せず、この確定値を`indexed_directories`として返す。
移行前に作成済みの索引は確定値を持たない。次回の正常な索引作成まで、CLIは`null`を返し、
MCPは省略可能な`indexedDirectories`フィールドを返さない。

### 5.4 ストリーミング書き込みとメモリ上限

走査した全ファイルの情報をメモリ上へ蓄積してから一括保存してはならない。ファイルメタデータは
列挙順に小さなバッチへ追加し、次のいずれかへ到達した時点でSQLiteの作業用テーブルへ書き込む。

- 1,000ファイル
- バッチが保持する推定メモリ16 MiB
- 前回の書き込みから2秒
- 走査の終了

これらは利用者向け設定にはせず、性能試験に基づいて実装定数として調整できるものとする。
ディレクトリ直下に1,000件を超えるファイルがある場合も、ディレクトリ完了を待たずにバッチを
書き込む。書き込み完了後はバッチのメモリを直ちに解放または再利用する。

SQLiteへの保存は次の方式とする。

1. 処理開始時に実行IDを発行し、その実行専用の作業用テーブルを用意する。
2. ファイルメタデータと走査済み相対パスを、プリペアドステートメントを再利用してバッチ挿入する。
3. 各バッチを短いトランザクションでコミットし、長時間の単一トランザクションを保持しない。
4. 全ディレクトリの走査とバッチ保存が成功した後、短い最終トランザクションで公開中の索引と
   作業用索引を切り替える。
5. 最終切り替えが成功した後、旧索引および実行IDに属する作業データを削除する。

差分更新でも、今回確認した全相対パスをメモリ上の集合として保持してはならない。走査済みパスを
SQLiteの作業用テーブルへ逐次保存し、走査終了後にSQLの集合演算で追加、更新、削除を確定する。

中断または失敗した実行の作業用データは公開検索から参照できないものとする。次回起動時に未完了の
実行IDを検出して安全に削除する。バッチが複数回コミット済みでも、最終切り替え前の旧インデックスを
完全な状態で利用できなければならない。

インデックス作成中のプロセス常駐メモリは、ファイル数およびディレクトリ数に比例して増加しては
ならない。事前ディレクトリ計数でも全パスをメモリへ保持せず、総数だけを保持して再走査する。
SQLiteのページキャッシュ、メモリマップ、チャネル、ログキューも明示的な上限を持たせる。
基準となる100万ファイルの性能試験では、インデックス作成によるピーク常駐メモリ増加量を
256 MiB以下とする。

### 5.5 差分更新と再構築

- `index build`は既存インデックスとの差分を反映する。
- `index rebuild`は対象ワークスペースのファイル索引をトランザクション内で再構築する。
- `workspace add`は登録後に`index rebuild`相当の処理を自動実行し、コンソールへ進捗を表示する。
- `workspace remove`は中央`Workspaces`テーブルの登録を削除し、外部キーの連鎖削除で
  対応する状態行とファイル索引行だけを削除する。他ワークスペースの行は維持する。
- どちらも事前計数とディレクトリ単位の進捗表示を行う。
- 差分判定には相対パス、ファイルサイズ、最終更新日時を使用し、本文ハッシュは使用しない。
- 削除されたファイルは、今回の走査結果に存在しない相対パスとして削除する。
- 失敗時は直前の正常なインデックスを利用可能な状態で維持する。

## 6. 性能要件

性能保証値は、実装前に固定した基準環境と公開ベンチマーク用ワークスペースで測定し、
リリース判定基準として別途確定する。少なくとも次を継続測定する。

- ディレクトリ数およびファイル数ごとの事前計数時間
- 初回インデックス作成時間
- 無変更状態の差分更新時間
- 1件追加、変更、削除時の差分更新時間
- インデックスデータベース容量
- ファイル検索の中央値および95パーセンタイル応答時間
- インデックス作成中の最大メモリ使用量
- ファイル数を10倍にした場合の最大メモリ使用量の増加量
- 各バッチの件数、書き込み時間、コミット回数

性能試験では、インデックス作成中に対象ファイル本文を読み取っていないことも検証する。

## 7. データ移行

v1.xのデータベースはコード解析固有テーブルを含むため、v2.0.0ではその場で流用しない。
初回起動時に旧スキーマを検出した場合は、自動的に破壊せず再構築が必要であることを通知する。
利用者が`index rebuild`を実行して新スキーマを正常にコミットした後に限り、旧インデックスを
退避または削除できる。ワークスペース登録と許可設定は維持する。

## 8. セキュリティおよびプライバシー

- 中央`shiori.db`の`Workspaces`テーブルをMCPファイル検索の認可境界とする。
- `SHIORI_ALLOWED_WORKSPACES`は参照しない。旧`workspaces.json`は初回アクセス時に
  トランザクションで移行し、移行済みファイルとして退避する。
- 旧`indexes/<workspace-id>/shiori.db`はワークスペース、状態、ファイル索引を
  中央DBへトランザクションでコピーした後、旧インデックスディレクトリを削除する。
- インデックス作成CLIの位置引数`<workspace>`と検索CLIの`--allow`は、中央`Workspaces`
  テーブルへ登録済みのパスだけを受け付け、未登録パスを暗黙に追加しない。
- ファイル本文、検索語、ベアラートークンをログまたはインデックスへ保存しない。
- 除外対象のパスやメタデータをインデックスへ保存しない。
- 再解析ポイントを経由してワークスペース外へ移動しない。

## 9. 受け入れ条件

1. インデックス作成時に通常ファイル本文を開かないことを自動テストで確認できる。
2. コード検索、Tree-sitter、ripgrep、LSP関連の公開機能と配布依存関係が存在しない。
3. 除外後のディレクトリ総数と実際の完了数が一致する。
4. 進捗表示が`0/N`から`N/N (100%)`まで単調増加し、逆行または分母変更がない。
5. 対話コンソールとリダイレクトの双方で進捗を機械的に確認できる。
6. アクセス不能、列挙失敗、SQLiteコミット失敗時に終了コード`1`となり、旧インデックスが維持される。
7. 追加、変更、削除、除外設定変更後の差分更新結果が完全再構築結果と一致する。
8. 許可ワークスペース外のパスが検索結果およびインデックスへ入らない。
9. 100万ファイル相当の試験でも全メタデータまたは全パスをメモリに保持せず、バッチ件数の上限と
   ピーク常駐メモリ増加量256 MiB以下が守られる。
10. バッチ保存後に強制終了しても旧インデックスが検索可能で、次回起動時に未完了データを回収できる。
11. 公開ベンチマークにより、確定した性能基準を満たす。

## 10. リリース時の文書更新

実装完了時にREADME、コマンドリファレンス、設定リファレンス、MCP設定ガイド、
セキュリティポリシー、アーキテクチャ、正式仕様書、リリースノートを本仕様へ同期する。
v1.xから削除されるMCPツール、CLIコマンド、設定項目、配布依存関係を移行ガイドへ明記する。
